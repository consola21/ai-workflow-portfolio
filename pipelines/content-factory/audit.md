# audit

```
schedule:  CRON_TZ=Asia/Seoul 46 8 * * 2
connects:  Claude 예약 작업 API(list_triggers, fire_trigger), Google Drive, Metricool
output:    주간 점검 보고 + (필요 시) produce 1회 재실행
```

## 실행 지시 (원본에서 내부 정보만 치환)

매주 화요일 자동 실행. 카드뉴스 주간 점검을 하고 결과를 보고한다. 질문하지 말고 끝까지 진행한다. 게시·예약·삭제·파일 수정은 하지 않는다(3번 재실행만 허용).

### 절차
1. **날짜 계산(코드로):** 지난주 목요일과 이번 주 월요일(어제). 이 둘이 점검 대상 게시일.
2. **제작 상태 확인**
   - `list_triggers`로 produce 작업(`<PRODUCE_JOB_ID>`)의 `enabled`, `last_run`(status, fired_at, failure_reason) 확인.
   - 드라이브 하위 폴더를 모두 나열(다음 페이지까지)하고, 게시일마다 해당 날짜 폴더와 `슬라이드원고.txt`·`캡션.txt` 존재 확인.
   - 판정: 폴더와 두 파일 있음 = 성공 / 없음 = 실패 / last_run 실행 중 + 3시간 이내 = 진행 중.
3. **재실행:** 이번 주 월요일 회차가 "실패"일 때만 `fire_trigger`로 produce를 **1회** 실행. 함께 보내는 지시: "정기 실행 결과물이 드라이브에 없음(last_run 상태: …). 빠진 회차를 만들되 게시일은 오늘(화)로, 폴더가 이미 있으면 중복 생성하지 말 것."
   - 지난주 목요일 회차가 실패였다면 재실행하지 않고 보고만(이미 지난 게시일).
   - 작업이 꺼져 있거나 진행 중이면 재실행하지 않는다.
4. **게시·성과 확인 (Metricool)**
   - 게시물별: 일시, 유형, URL, 도달, 조회, 좋아요, 댓글, 저장, 공유, 팔로우.
   - 지난 7일 계정: 팔로워, 증가, 감소. 앞으로 14일 예약 게시물.
   - 폴더는 있는데 그날(또는 다음 날까지) 게시물이 없으면 "게시 누락 가능".
5. **해석 규칙:** 확인된 사실 / 추론 / 모름을 구분. **게시물 3건 미만이면 숫자만 보고하고 판단하지 않는다.** 3건 이상이면 회차별 저장·도달을 비교하고 가장 나은 회차와 이유(추론)를 한 줄로. 게시 요일 차이를 함께 적는다.
6. 보고 문장을 humanizer로 다듬어 보낸다(숫자·판정·날짜는 그대로).

### 보고 형식
결론 1줄 → 1. 제작 상태(판정·근거·재실행 여부) → 2. 게시 상태 → 3. 성과 → 다음 할 일 최대 3개
